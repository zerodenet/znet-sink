# Plugin management page document and invocation boundary

This change binds a desktop management page to the actual signed page and component materials. It does not enable plugins on Android/iOS, provide a mobile execution container, or claim mobile VPN acceptance. The host fixed navigation and the existing guest SDK v1 protocol are preserved.

## Document and original authority

`plugins_page_document(pluginId, pageId)` verifies the installed package through the existing Store/rescan path, renders the signed page, and captures component views and their actual Manager registration/revision under the Host operation lock. Its response contains `plugin_id`, `page_id`, `html`, `components` and an opaque `document_review`. The store holds at most 16 documents for 15 minutes each; nothing is persisted. The binding records the rendered page SHA-256, component material digests, original component reviews, deadline and a shared cancellation flag. An old document cannot acquire newer authority after revoke/re-authorize, configure, update, uninstall/reinstall, changed page/material or Host closure. Components without a usable review can remain visible as blocked metadata but cannot execute.

The desktop-only, main-window-guarded RPCs are:

- `plugins_page_check(documentReview)` rechecks the existing document without creating a replacement authority.
- `plugins_page_close(documentReview)` removes the document and cancels all original page invocations.
- `plugins_page_configure(documentReview, review, values)` and `plugins_page_invoke(documentReview, review, action, payload)` use the reviewed Host wrappers under their owning operation lock. Configure returns the actual new snapshot and retires the old document; it does not reuse that document after its own revision change.
- `plugins_page_file_preflight(documentReview, review, call)` checks the actual FileRead/FileWrite method, capability and original review before the host picker. Its reply means `permission-checked`, not that a file was selected or a one-time system grant was obtained. The actual SDK call after selection must submit the same original review and document, so changes during the picker invalidate it.
- `plugins_page_sdk_call(documentReview, review, call)` admits using Authority `begin_host_call_at_revision`, preserving the original registration/revision and shared cancellation flag.
- `plugins_page_protected_load(documentReview, review, call)` validates the original lease before consuming the opaque owner-bound sensitive material. Validation/composition remain host-side and runtime-only. The existing authorized configuration apply returns its real runtime receipt; no ordinary configuration file/database export is used.

Frontend reviews are injected by the trusted host frame; they are not read from guest messages. Page metadata calls also check the original document. The final callback must still match its original channel/window and document; a late result cannot be delivered to a newly opened frame.

## SDK execution, budgets and platform effects

Generic SDK execution is admitted with the original component lease `execute`, and its result is extracted with that same lease's `Resource.take`. Managed subscription methods retain the existing domain-owned authorized transaction callbacks, each bound to the original page/lease; protected runtime application retains its existing original-lease asynchronous execute/resource boundary. Existing native file/network adapters may additionally establish a narrower selected-path/origin policy; that native IO policy never replaces the original component epoch. The original component lease is checked again immediately before delegated native IO and after awaiting/returning its result. Secret insertion, storage, scheduler and other SDK operations run inside the original execution envelope. Persistent secret/crypto operations recheck after acquiring the Host operation lock.

The management page has its own bounded `Call` lease, with the existing SDK validation and a maximum resource/result budget of 8 MiB, not an unbounded transport. Ordinary VM invocations retain the component manifest's existing `max_calls` and `output_bytes` limits. SDK receipts now participate in that original resource reservation: processing a large response and later emitting a small VM summary does not exempt the intermediate receipt from its invocation budget. Oversize results fail explicitly; they are not truncated or passed using a fresh policy. Reservations are released on resource extraction/drop; the operation call count remains charged. The SDK call's own result and elapsed-time checks still apply.

BrowserOpen prepares only a checked URL in the SDK conversion. The actual OS opener runs in the backend through the original lease execution boundary; its receipt is `accepted` only after the opener accepts the request. This is not proof of browser rendering. The frontend does not open the URL a second time. Protected configuration application uses its existing original-lease asynchronous execute/resource extraction boundary and returns only the actual runtime identity/receipt.

VM-originated FileRead/FileWrite cannot treat a guest `selected_path` as a trusted system selection: the VM dispatcher rejects these requests until a host-owned picker/opaque selection-ticket adapter exists. This does not remove the management page's host-picker flow, where the frame replaces guest path claims with the actual user-selected path after preflight and rechecks the original document/review. Lifting the VM restriction requires a real host-created, scope-bound selection ticket and lifecycle checks, not a broader `user` permission or raw guest path.

`pageClose` and normal Host exit deny new calls and invalidate delivery from the original in-flight leases. They do not withdraw a network request already sent, undo a file already published, revoke an OS browser request already accepted, or roll back a confirmed local write. Closure/expiry/revocation after an effect produces a delivery-denied/unknown result, never unconditional rollback. System effects cannot be atomically cancelled with a policy update; the owning lease admission, immediate checks and final extraction make that limitation visible.

Known original lease/admission errors are mapped directly from Rust enums to the existing SDK wire codes (`budget_exceeded`, `deadline`, `revoked`, `expired`, `disabled`, `cancelled`, `busy`, `permission_denied`). A document lease expiring is distinct from an explicit page close, and both are distinct from a component revision change. These typed failures use fixed host messages and exclude arbitrary original error text, paths and detail fields; ordinary IO/package errors retain their existing sanitizer. No error category is inferred from strings.

## Verification

Focused Rust tests use a real signed package, installed Store, real Host rescan and actual Manager policies. They cover document/lease closure; revoke/re-authorize ABA; document count/expiry/Host exit; foreign review/method-capability rejection; in-flight delivery denial and prevention of later effects; a real selected-file read under a fresh native IO policy whose result remains denied by the revoked original component; protected material remaining intact when original permission is absent; and corruption of the real installation store cancelling both the document and its original in-flight binding.

The 11 focused cases also exercise an actual one-byte original resource budget, an actual elapsed lease deadline, real revoke/close/document expiry, and canaries proving typed failures cannot copy arbitrary messages/details. Run `cargo test --manifest-path src-tauri/Cargo.toml --lib services::plugins::page_channel`. Frontend channel tests and browser tests are owned by the frame implementation and recorded separately. No live external browser, third-party HTTP request, system picker or mobile plugin execution is claimed by these Rust tests.

## Browser transport boundary

The host bridge additionally bounds each frame to 512 requests, eight in flight, 256 KiB request JSON, 1 MiB result JSON and 4 MiB total delivered results. These are transport limits, distinct from the SDK's per-call native budget and VM execution limits; an oversized reply is rejected explicitly. Component identity, registration and revision must be safe integers in this existing DTO domain; unsafe values are refused rather than truncated.

Production `src/app.html`, native Tauri CSP and the browser fixture all use `frame-src 'none'`. Signed pages are loaded only through sandboxed `srcdoc`; URL frame navigation is blocked. Initial iframe load does not synthesize guest readiness: the exact current window and fresh channel must send the trusted bootstrap ready/load messages and complete a host acknowledgement round trip. Recognized ordinary requests before acknowledgement consume the normal transport budget and are rejected without invoking a component or platform effect. A parent load callback alone does not prove navigation: [iframe load tasks](https://html.spec.whatwg.org/multipage/document-lifecycle.html#completely-finish-loading-a-document) and [posted-message tasks](https://html.spec.whatwg.org/multipage/web-messaging.html#posting-messages) use separate task sources. Subsequent callbacks therefore pause admission/effects and delivery while the existing bootstrap answers a fresh host nonce using its private per-document proof and captured original Document. The exact window, channel and original epoch must still match. Existing transport tickets wait within the same eight-in-flight budget; no new business queue, operation ID, review or replay is created. If the original document cannot answer within the five-second UI handshake budget, the original document is closed; a pagehide message whose original window/channel can be verified closes immediately using the trusted capture listener installed before guest code. Browsers may discard the source window of a message emitted during destruction; that message cannot replace the exact-window guard. A replacement that cannot prove the original document then closes through the bounded document check, with an explicit unverified-document reason. Detached frames and old channels cannot validate a replacement. Tauri CSP configuration behavior was checked against the [official CSP documentation](https://v2.tauri.app/security/csp/). Chromium tests verify signed content still runs and no remote navigation request is emitted. Actual WebKit and platform WebView evidence is recorded separately, not inferred from Chromium.

The locked Tauri 2.11.2 `manager::set_csp` implementation can add `script-src`/`style-src` asset hashes even when the configured policy contains only `frame-src`. Those parent directives would be inherited by `srcdoc` and reject the signed dynamic bootstrap/content. This narrowly introduced parent policy therefore disables Tauri's automatic modification of those two directives explicitly; it does not introduce a parent script/style restriction. The signed child retains its separate restrictive CSP. The executable configuration test fixes this native setting as well as the production/harness frame restriction, so a future automatic policy change must be reviewed and tested.


Native receipts are bounded to 1 MiB before waiting for document validation, with a separate per-epoch 4 MiB aggregate reservation for held content. Normal resumed effects and delivery recheck the original host document, so silent revocation/expiry during validation cannot acquire replacement authority. A confirmed configuration save is the specific exception: that owning write intentionally changes the review and closes the original backend document. Its already-confirmed, bounded host snapshot may update the same current host view after same-document proof; then the old page retires. It neither invokes with the changed review nor sends it to the guest. A navigation/closure still denies that old page callback; no write is replayed.


## Document-bound reply transport

The fresh bootstrap creates a private MessageChannel before signed guest bytes execute, retains its document-side port in its closure, and transfers only the host-side port with the original ready message. The host captures that port once as an immutable delivery target while retaining the original Window identity for inbound checks. Ready acknowledgements, errors and business receipts use that captured port; safe lifecycle challenges alone use the Window transport. A later document cannot inherit a WindowProxy-targeted plaintext receipt. Retirement closes the original port; old epochs cannot retarget delivery to a replacement.

Business requests additionally carry the bootstrap's private document proof and require the exact original Window/channel/proof before dispatch. The bootstrap captures the frame WindowProxy before guest code and checks its active Document before requesting, responding to lifecycle checks or consuming receipts. The public SDK v1 methods and SDK Call/Reply DTO remain unchanged; document tokens, component reviews and the private port/proof are not exposed through guest context APIs.

A CSP-denied URL navigation can retain the original document in WebKit. The invariant is zero forbidden requests and no authority or receipt crossing a genuine document replacement, not unconditional closure merely because a navigation was attempted. Browser regressions use actual policy violations/HTTP probes, then a real replacement and a request carrying the old known channel before the parent's load callback. The replacement must neither invoke a component nor receive the original held receipt.

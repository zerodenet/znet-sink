# 2026-09-06 客户端显示与运行日志核查

基线：客户端 `0.0.16-rc.202609061153`，代码 `a431fc8`。本次修改仅在客户端仓库；没有安装、重启正在运行的客户端或内核，也没有修改本机代理、TUN 或 DNS 设置。

## 已确认的问题与修复

### 运行时长

概览原先将 `now - startedAtUnixMs` 直接向下取整为分钟，因此启动后 59 秒内一直显示 `0 分钟`。保留已有每秒时钟和内核实际启动时间，改成秒、分、小时、天的进位展示。刷新快照、返回页面或切换界面模式不创建新的计时基线；停止或状态过期时继续显示不可确认状态。

### 网络地区

专业概览原先仅将地区放在提示信息中。现在 IP 旁显示客户端内置国旗，并直接显示国家/地区、区域和城市。支持 ISO 国家码及常见中英文名称；未知地区显示明确占位。移除旧概览中已经不使用的远程国旗地址和重复映射。

### 日志渲染

安装版日志页不断累积已加载行，每次刷新又重新构建所有行对象。检查时已有超过 1500 行进入视图。初始加载 400 条大型结构化日志的浏览器场景记录到 801 ms 长任务。

- 使用带行高测量的可见窗口，仅挂载可见行及少量缓冲行；完整历史、详情、搜索和复制仍基于已加载数据。
- 相同页面刷新保留记录和数组身份；使用浅层状态及搜索缓存，减少重复代理和序列化。
- 日志信号按一秒合并，隐藏窗口暂停后台查询，页面销毁后作废旧请求并清除定时器和观察器。
- 阅读历史时保留滚动锚点；行高更新放到下一帧，避免 ResizeObserver 在同一次交付中循环修改布局。

同类场景修复后最长长任务约 246–304 ms（同时编译客户端时一轮测到 428 ms）；增加到 801 条并测试展开、搜索、刷新、历史加载后，DOM 行数仍少于 50。系统 WKWebView 首屏测得 23 行，没有窗口错误。这些是本机测试场景结果，不能等同于所有负载下的性能保证。

### 前端错误可定位性

提供的错误 #92932 是 20:28:00（UTC+8）的第三条不透明 `Script error.`；前两条发生在 20:27:22 和 20:27:24。最后一次页面加载记录是节点页，随后才切到连接和日志页。因此不能断言这三条错误由日志页造成。

全局异常现在附带当前页面、正在展示的页面、界面模式、设置分组、可见性及可获得的原始异常名称和栈。跨 realm 的错误对象不再被 `instanceof Error` 丢弃。页面和设置分组增加渲染错误边界，保留具体错误并允许重新打开页面。对于 WebView 本身已隐藏的堆栈，只能明确记录为不透明错误，不能补造原因；原有三条错误的直接原因尚未证明。

### 内核继承客户端文件句柄

进一步检查发现 20:23:43（UTC+8）约 100 ms 内出现 30 条内核 `inbound accept error: Too many open files (os error 24)`。这是真实的接入失败，不是界面提示。检查时内核数值描述符中有约 90 个普通文件，包含客户端的 Metal、CoreImage 和界面恢复资源；桌面启动环境 `launchctl limit maxfiles` 显示默认软上限为 256。没有取得该历史瞬间的进程 rlimit，不能声称已直接测得当时的精确上限或排除其他并发因素。

正常启动、崩溃重启和候选内核预检查统一使用内核启动器：

- Unix 子进程在 exec 时关闭标准输入、输出、错误以外继承的文件句柄，保留 Rust 的 exec 错误通道直到 exec 完成。
- 子进程软上限提升至至少 4096，受原硬上限约束；保留已有更高限制。父进程和系统限制保持不变。
- Linux 优先使用 `close_range(CLOSE_RANGE_CLOEXEC)`，不支持时使用逐描述符 CLOEXEC；macOS 通过 `proc_pidinfo` 列举实际句柄后设置 CLOEXEC，避免高软上限下扫描百万个空槽；缓冲不足时保留完整扫描回退。Windows 保留已有标准句柄创建方式。

该修复不要求更新 Zero 二进制，但需要新客户端重新启动托管内核才会生效。

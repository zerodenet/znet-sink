# 客户端统一能力入口、管理与执行管道：实施方案

2026-09-12，根据用户最终明确的主轴重写。**已开始 P0/P1 本地重构；入口矩阵、实际迁移、验证与余项见 [实施记录](./capability-migration.md)。** 目标是客户端自身拥有一套能力入口、管理路径和执行管道；内置功能、插件及其他外部调用都是其调用者。配置文件依赖是配置能力内部必须解决的一项，不再以配置来源管理组织整个插件体系。

本文取代前版“先围绕配置资源建立整个框架，再开放插件”的组织方式，保留已核对的配置事务、内存应用、安全和迁移约束。ZBoard 是业务验收场景，不是客户端的业务模型。

## 1. 核心边界

- **一个入口边界**：UI、内置业务、插件 SDK、外部调用适配器都进入客户端能力入口。可以有不同传输/语言适配和类型化方法，但不能各自执行权限检查后另走后台。
- **一个管理责任方**：ZNet Sink 管理调用身份、授权、任务、资源句柄、预算、取消、恢复和结果。插件推动业务、发起请求，不拥有独立的执行后台、凭据旁路或内核管理器。
- **一条执行管道**：所有请求先经过共同管理步骤，再分派给对应能力执行模块，最后由共同管理路径核对并发布结果。同一种操作只有一个生产执行实现。
- **模块仍按能力分工**：网络、文件/存储、密码学、通知、配置与内核适配各有模块。统一不等于单一巨大函数、统一串行队列或把所有操作硬套配置状态机。
- **没有内置旁路**：内置功能不能因为不是插件就直接发网络、写受管理数据或调用内核来绕过能力服务。它们的用户意图/授权来源可以不同，资源保护和执行管理仍有效。
- 文件、密文、内存材料只是输入/存储形态，不决定另建运行链。平台差异由能力适配器承接，不向插件暴露 PID、原始路径或内核 IPC。
- 独立进程/OS 沙箱不是当前前置条件；采用客户端统一管理的独立 VM。签名包安装不代表授予权限或允许自动运行。

## 2. 统一入口与执行管道

```text
内置界面 / 内置业务编排 / 插件 SDK / 外部调用适配器
    → 客户端能力入口（可信建立调用身份，类型化请求）
    → 统一管理（权限、资源归属、任务、预算、有效期）
    → 能力分派
        网络 / 浏览器回调 / 存储文件 / 密码学 / 通知 / 配置运行
    → 对应执行模块及平台、内核适配器
    → 统一完成处理（核对授权代次、实际结果、资源生命周期）
    → 有权接收的结果、状态或受保护句柄
```

“一个入口”不是给插件暴露 `invoke(any_command)`，而是只能调用已登记的类型化能力。每项能力明确请求、权限范围、结果类型、预算、取消/副作用及敏感数据处理规则。内部纯计算 helper 可直接复用；有授权或资源/副作用边界的执行不能绕过管理层。

共同模型在 P1 固定，名称仅作概念说明，实施时沿用现有结构：

| 模型 | 所有者及约束 |
| --- | --- |
| 调用上下文 | 宿主建立调用者、插件/组件身份、用户意图与授权代次；插件不得自报 internal 身份 |
| 能力请求 | 指定操作与目标范围；不接受任意内核命令、主机对象或隐式全局权限 |
| 操作记录 | 客户端记录操作 ID、父任务、阶段、资源关联和必要结果；受容量/保留期限制，不保存敏感正文 |
| 资源句柄 | 客户端管理网络响应、文件、秘密缓冲区、配置材料等；绑定所有者、权限、有效期和代次，ID 不是授权证明 |
| 完成回执 | 客户端确认真实完成或不确定状态，并按权限投影；不能由插件伪造内核应用成功 |

组合能力内部调用其他能力时继承原调用上下文和预算，不能通过客户端代执行获得额外权限。由客户端自身负责的恢复/清理使用明确、有限的管理职责，只处理归属正确的操作和资源，不借此替插件发起新的业务请求。

## 3. 统一管理，不统一所有业务步骤

插件自己决定登录、拉取、解析、刷新或连接的业务顺序。每一步涉及网络、存储、解密、投递或内核运行时，均请求客户端能力执行。内置业务同样如此。客户端不理解 ZBoard 登录协议，也不替插件完成 OAuth 业务。

一次业务流程可以关联多个客户端操作，以便统一取消和追踪；它不是一个跨网络、磁盘、内核的自动原子事务。任何能力不得承诺把已发送的网络请求或已提交的内核修改“取消得像没发生过”。

管理层统一掌握：

- 启停与任务归属：组件停用、卸载、来源/资源失效都经过同一清理规则；插件回调不是清理成功的前提。
- 并发与预算：每能力/资源按需限流，配置提交按目标串行；网络等待不持有配置锁，不用一把全局锁阻塞全部功能。
- 授权撤销：执行前、敏感能力调用和交付前校验；已提交副作用由对应执行模块核实并按条件清理，不能仅丢弃结果后宣称已撤销。
- 恢复：由客户端恢复必要操作状态与用户意图；不自动重放不可证明幂等的请求。需要插件继续编排时报告等待插件，不能复制其登录/通信逻辑。
- 数据流转：敏感响应、解密材料与内核配置可通过句柄在执行模块间传递，禁止为了跨模块复用而经前端、普通 JSON 日志或临时明文文件中转。

来源注册、外部数据投递也是受控操作。插件可以投递普通材料或受保护句柄，客户端校验归属、格式、大小与策略；不能直接写入活动 profile、替换运行配置或接管持久化位置。

## 4. 能力范围、用户授权与开发者 SDK

以下是能力族，不是本轮全部开放的 API 清单：

| 能力族 | 宿主负责 | 插件负责 |
| --- | --- | --- |
| 网络 | origin/目标范围、方法、重定向、凭据使用、大小/时间与敏感响应去向检查 | 登录/面板协议、公告订阅请求和解析 |
| 浏览器与回调 | 受限打开入口、回调归属与一次性句柄路由 | OAuth 提供者流程与业务会话；与实际服务端协议协作 |
| 数据/文件 | 独立命名空间、容量、用户选定文件句柄、加密存储、读取/导出政策 | 缓存内容、更新时机和业务含义 |
| 密码学/秘密使用 | 标准密码学操作、受保护缓冲区/句柄、生命周期与用途约束 | 通信信封、协议版本、数据获取与流程驱动 |
| UI/通知 | 展示入口、来源标识、内容与频率限制、用户权限 | 公告内容与提醒时机 |
| 配置与运行 | 受控接收材料、统一合成、内核应用/断开、安全状态回执 | 何时请求准备/刷新/使用某份订阅 |

不定义 ZBoard 登录、公告读取、套餐查询等宿主业务权限。不提供“任意内核命令”能力。SDK 与内置调用入口共用执行服务，避免复制 HTTP、存储、配置或任务后台。

有效许可同时受注册上限、组件声明、用户授权、资源政策和平台能力约束；用户不能通过普通确认框使插件突破资源保护。插件安装不授权，允许网络不自动允许存储/通知/配置应用。身份由宿主在可信入口创建，插件不能自报 internal/user 身份；材料/任务句柄绑定组件、资源和授权代次，不接受任意 ID 作为授权证明。该模型在 P1 建立并用于内置入口，插件桥和用户界面沿用此模型，不是接入插件时才补权限。

设备/执行能力约束同样在 P1 的服务边界表达，平台具体 adapter 在有对应实施目标时接入；不让文件路径、PID 或桌面专属对象渗入公共 SDK，避免到 P5 才发现必须重做模型。

授权 UI 展示客户端定义的可信权限名称、目标和范围，插件用途说明作为附加不可信描述。支持必需/可选、拒绝、记住同一范围的选择及撤销。记住的用户选择与执行中的短租约分开；权限扩展、跨源/跨账号和敏感角色变化必须重新确认。升级后重新验证身份/声明，旧执行句柄失效。

敏感配置优先通过客户端密码学/内存能力得到不透明材料句柄，再由同一个客户端服务合成并传给内核。插件不持有直连内核通道。若插件自行把明文变成普通 JS 字符串，则无法保证宿主替其消除全部 GC 副本；高敏感路径需要约束 SDK 与插件准入，不能仅靠弹窗授权承诺保密。

### 插件管理外壳与插件页面分层

插件列表和详情页采用两层边界。客户端固定展示插件名称、说明、版本、发布者、启用状态、兼容性、可信权限、更新和卸载；一个安装包只占一张插件卡，内部多个组件不得各自复制成卡片。插件不能改写这些信息的布局、伪造启用状态、隐藏权限或替换卸载入口。长版本、插件 ID 和发布者使用单行省略并提供完整悬浮文本，避免插件元数据破坏统一布局。

插件管理主页面只展示已安装插件及其搜索、检查、启停和详情入口，并与规则集、订阅一样支持列表/卡片切换。安装属于低频任务，统一收进一个“安装插件”窗口：市场目录、线上发行详情、本地来源确认和安装进度都在窗口内部切换，不叠加第二个模态层。“从本地安装”位于目录刷新动作之后。首次线上安装直接采用插件中心登记的最新兼容正式版；版本选择只在已安装插件的版本管理中出现。线上与本地安装最终进入同一签名、身份、兼容性、版本和完整性校验流程。

插件自己的业务说明、复杂配置和管理流程属于签名插件页面，不应被压进客户端通用弹窗或少量固定字段。客户端在插件详情中提供独立页面容器和安全导航；插件可声明 `management`、`about` 等 surface，并在自己的 UI 内组织多步骤流程。简单插件仍可选择宿主渲染的声明式配置作为兼容路径，但它不是复杂插件的唯一交互模型。

宿主声明式配置只保存非敏感、可审查的静态设置。账号密码、服务私钥、公钥指纹输入、设备密钥、会话和续期凭据不得为了复用通用表单而降级成普通配置字段。涉及远端插件发现、自动身份/密钥协商、临时秘密输入、授权、资源列表和选择的流程，由签名插件页面组织，并通过宿主的秘密、密码学、网络和来源能力执行；插件页面只拿不透明句柄和安全投影。

插件页面不是任意远端网页，也不能取得主界面 DOM、Tauri 命令、宿主 Cookie、文件路径或直接网络权限。页面资源必须随安装包签名和校验，运行在独立不透明来源的受限容器；页面与插件服务组件之间只通过带插件/组件身份、授权代次、预算和取消语义的类型化消息通信。网络、秘密、调度、来源投递和内核操作继续进入统一能力管道。停用或卸载插件时，客户端销毁页面、撤销消息桥并回收对应服务任务。

客户端不得把 surface 名称存在当作页面已可用的证明。签名 UI 资源、隔离容器、消息协议、导航生命周期和负面安全测试全部完成后，才加载插件页面；缺少页面资源时详情页只展示宿主信息和已支持的声明式配置。

#### 2026-09-16 客户端已落地边界

当前桌面客户端已经实现以下宿主契约，后续 Connect 插件按这些接口实现自己的页面和业务：

- 安装登记、发布者指纹、组件启用意图、已批准权限及完整已审声明由客户端持久化。停止组件保留用户同意，显式“撤销权限”才清除同意；客户端重启后会重新校验缓存登记、签名包、发布者和声明，再恢复仍然有效的启用意图。
- 本地安装与 GitHub Release 在线安装先生成候选审查结果。更新新增权限或扩大 scope 时，客户端展示组件、权限和精确 scope，并要求对候选包摘要作显式确认；更新完成后组件保持停用，新增权限仍需在权限页批准。删除权限或声明子集不会凭空增加授权。
- 安装包可携带由发布者签名的 `management` 页面。客户端只加载包内已验签资源，使用不带 `allow-same-origin` 的脚本沙箱、禁止直接网络和表单提交的 CSP，以及每次加载随机消息通道。页面不能调用 Tauri、指定其他 plugin ID 或跨插件访问；客户端根据当前详情页绑定真实插件和组件身份。
- 页面 SDK 目前提供上下文、宿主声明式配置、插件自己的 `state/cache` 命名空间以及受控组件调用。配置、权限、启停、更新和卸载仍由客户端固定页面负责；插件页面负责登录、源管理、订阅选择、自检结果等业务交互。
- `state/cache` 以发布者指纹和插件 ID 双重命名，限制键、单项大小、总量并原子写入。值由插件作为 Base64 不透明数据处理，客户端不解密、不把账号密码定义为普通配置，也不声称这些文件能抵抗同一系统用户下的恶意本地进程。Connect 应只临时使用账号密码，并持久化远端签发的设备/续期凭据。
- 组件可声明 `host_start` 生命周期事件。客户端仅在组件仍启用且原签名、发布者、权限声明和配置均通过复核时执行一次有界启动调用；调用可读取不超过 8 KiB 的插件不透明运行态快照，并以版本化结果信封原子更新状态。这个入口用于插件自行判断会话并向远端续期，不让客户端实现 ZBoard 登录协议，也不提供常驻线程。
- 用户同意与单次执行租约已经分离。持久同意没有“最多 10 分钟”的用户语义；每次调用仍由客户端创建内部预算、取消和代次检查，停止、撤权、升级、卸载或退出会立即使在途调用和晚到结果失效。内部租约不作为凭证交给插件。

2026-09-17 已在上述基础上完成通用插件 SDK v1：逐项授权的存储管理、通知、后台调度、浏览器打开/一次性回调、用户文件选择、短期秘密/材料句柄、受限密码学操作，以及“受保护材料 → 配置合成 → runtime-only 应用”。Rust/TypeScript SDK 不接受插件身份或宿主命令名，管理页桥从已验签上下文绑定真实组件；时间、参数、结果、频率和资源数量均有上限。停用、撤权、升级和卸载会回收相关资源。详见 [插件 SDK v1](./plugin-sdk.md)。Connect 完整登录、设备凭证续期、订阅关联和消息流程继续由插件与 ZBoard 服务端实现。

## 5. 用同一管道检验内置功能与插件

以“读取订阅并运行”为例，两种调用者均经过相同能力实现：

| 步骤 | 内置功能 | 插件 | 客户端统一执行责任 |
| --- | --- | --- | --- |
| 获取数据 | 内置业务请求网络/文件能力 | 插件按自己的协议请求网络/文件能力 | 权限、传输、目标和资源预算 |
| 解密/解析 | 按输入格式组织必要步骤 | 按业务协议组织必要步骤 | 提供受控密码学/材料能力；不实现面板业务协议 |
| 投递材料 | 调用材料提交能力 | 调用同一能力 | 检查句柄/正文、归属和保护政策 |
| 应用配置 | 发起应用请求 | 发起同一能力请求 | 合成本地覆盖、校验、唯一内核适配、确认实际结果 |
| 取消/恢复 | 表达用户意图 | 请求任务操作或继续业务 | 统一任务、授权、资源清理及运行状态管理 |

普通本地导入无需执行不存在的网络/解密步骤，但它已有的文件读取、材料投递和应用操作仍走统一管理路径。统一不要求每个业务经过相同长度的流程，要求每一步相同的能力都没有第二个执行入口。

只有客户端持有到内核的真实控制通道。mixed 端口、绕过 IP 等设置也通过统一配置能力处理；内置设置页面不能直接写配置来绕过插件所使用的配置执行服务。

## 6. 配置执行能力内部的统一实现

### 配置资源与运行材料分开

`ConfigResource` 是客户端内部可按策略持久化的描述，**不直接作为 UI/插件返回对象**：稳定 ID、来源引用、所有者、源版本、内容摘要、访问/存储策略、允许的本地覆盖及安全展示字段。其材料可由文件读取、内置订阅或插件投递，来源信息不得携带秘密 URL 或凭据；这些使用独立秘密存储引用。另设允许列表生成的公开 view，不默认暴露来源定位、账号标识、内容摘要或内部版本；普通配置也经过这一投影边界。

`ConfigMaterial` 是客户端执行服务内短时持有的实际配置，受类型和生命周期约束。普通来源和受保护来源最终都交给相同的解析、校验、合成、提交逻辑；不经前端 JSON 往返，不把受保护材料装进通用可序列化 profile。

`LocalOverrides` 是用户可管理的客户端设置，独立于来源正文保存，具有自己的 revision。必须明确归属：监听端口/监听范围等设备设置属于设备级；用户主动选择的资源专属覆盖按资源 ID 保存；运行中的临时选择属于实例级。P0 对照既有设置逐项确定，禁止把所有覆盖变成全局或在切换来源时隐式复制。合成读取三者的固定版本快照，资源切换不清空设备设置、不把来源 A 的专属覆盖带给 B。

`EffectiveConfig` 只作为提交内核的候选运行材料。UI 与插件获取安全报告和操作回执，不默认拿到最终配置全文。

### 策略维度独立

- 访问：是否允许正文读取、编辑、复制、导出、诊断披露。
- 持久化：普通可读存储、设备加密存储、仅内存；遵守来源的最低保护要求，调用者不能自行降级。
- 恢复：从保存的普通材料、解锁密文或调用来源重新获取。这里只返回材料/不可用原因，不控制内核生命周期。
- 来源权限：插件/组件、源实例、账号/资源句柄、授权代次及到期时间。

“来源是插件”不等于必须受保护；“来源是本地文件”也不决定所有出口必然可读。保护是资源政策，不以来源种类分叉整个架构。

### 配置提交与运行恢复

```text
已通过统一入口与管理层的配置请求
    → 取得有权使用的配置材料句柄（不占提交锁）
    → 统一校验 + 客户端允许的本地覆盖 + 强制安全策略
    → 再检查来源版本、覆盖版本、授权代次与内核实例
    → 唯一配置提交事务 → 唯一内核适配器
    → 确认实例/revision → 发布安全状态与按策略持久化
```

托管内核对所有来源采用同一启动流程：准备最小无秘密 bootstrap，建立控制连接，再经同一事务应用有效配置。必要的无秘密 bootstrap 文件允许存在，但不能把完整配置文件重新作为普通/受保护来源的分支条件。

#### 内核应用接口是前置核对项

复审只读核对：本地 Zero 的 `crates/api/src/command.rs` 声明 `config.apply_runtime`；`crates/engine/src/api/mod.rs` 将普通 apply 交给 `reload_config`，runtime apply 交给 `reload_runtime_config`。GUI 已迁入 `config.apply_runtime`，并验证目标二进制的 runtime_only 回执、监听器协调和启动文件不变；受保护出口与后续策略仍须单独验收。

目标是所有托管来源由同一 adapter 使用经过验证的 runtime-only 契约，客户端存储服务独立负责允许的持久化。核对必须覆盖目标发布内核、proxy 层监听器协调、回执语义及后续策略操作，不以本地 engine 函数存在作为发布物已经支持的证据。旧内核缺必要能力时，迁移前明确兼容/最低版本范围，不能静默针对普通来源退回文件链。普通与受保护来源共用应用接口，但后者还须通过日志/观测等保护能力检查。

普通配置仍能保存、编辑、导入导出；它们变成能力服务上的操作，并与托管执行解耦。用户外部自行启动内核的 CLI 行为不因客户端迁移被改变。连接外部内核时，统一适配器核对能力；达不到受保护要求则该资源不可用。

恢复由统一管理层调度：恢复描述和用户意图 → 经相应能力准备材料 → 合成 → 应用 → 确认。插件业务仍由插件推动，客户端不能为了恢复而自行实现插件的登录/取钥协议。插件缺失、网络被拒绝、密钥过期时显示等待条件；不另建插件重启循环，不自动重放已提交但结果不确定的操作。

运行事实、用户期望和本地保存状态分开。内核应用成功但本地保存失败时，要报告实际状态并恢复一致性，不能虚报回滚；uncertain 时通过操作回执/身份核对恢复，不能盲目重复提交。持久操作记录只含必要且按权限投影的内部元数据。

#### 撤销不等于撤回已经提交的内核操作

任务区分准备、待提交、已提交、已确认/结果不确定。准备和待提交阶段撤权后禁止发送；已经提交时，授权代次只能阻止后续调用和晚到结果被当成仍获授权，不能证明内核没有应用。客户端必须继续核对实际运行状态；若需清理，只清理属于该资源、操作及内核实例且仍为当前的运行结果，不能撤掉后续合法应用或无关连接。内核清理/回退若缺少可验证的条件控制，则保留明确的不确定状态并限制冲突写入，不能虚报“已取消”。不新增任务页或持久队列来代替这条事务规则。

### 本地覆盖与秘密边界

第一批覆盖 mixed/本地监听端口和局域网绕过 IP/CIDR；监听范围变化单独处理，因为从回环地址改为对外监听会改变网络暴露范围，不能作为改端口的隐式副作用。复用现有设置及合成函数，并逐项验证不会改动基础配置中的受保护字段。

其他现有覆盖（DNS、策略选择、测速参数、规则等）先建立对应表，普通配置保持现有明确行为；受保护资源只有经过审核的覆盖范围才启用，不能粗暴开放任意 JSON patch，也不凭默认值删除既有用户设置。

合成优先级为：来源基础 → 有权限的用户覆盖 → 客户端强制安全约束。日志正文、导出、控制面暴露、任意外部文件引用、事件输出等属于安全约束，不能被插件配置或普通覆盖重新打开。合法覆盖被安全策略拒绝时明确报错，不静默改变用户意图。

字段白名单与保护政策由客户端定义。来源可以声明最低数据保护要求，不能据此接管客户端的设备设置。对于已承诺给用户的端口/绕过设置，来源约束若与之冲突，应在选择/应用前显示不兼容原因，不能先应用再锁死用户设置；客户端不能通过普通覆盖降低正文保密要求。修改端口只需要本地覆盖信息，不应先读取配置全文。合成产生的最终材料不得自动写入普通导出、调试或差异预览。

## 7. 现有路径迁移与模块责任

已经核对的配置基础可以复用：`configuration/composition.rs` 的纯合成、`configuration/report.rs` 的路径报告、`configuration/apply.rs` 和 `engine-client` 的应用确认。profile content、`export_active`、`runtime_host/start.rs` 与完整文件的耦合必须在配置能力内部解除。

客户端既有网络下载、系统探测、文件发布、桌面打开/剪贴板、TUN/系统代理/模式切换和诊断工具入口已经完成调用盘点并迁入共同管理契约；插件通知、调度、浏览器回调、用户选取文件、短期秘密/密码学和受保护运行时加载也已接入 SDK v1。各能力仍须分别通过权限、预算、撤销和生命周期测试，不以接口名称代替验收。

模块职责：

- 客户端管理层：能力入口、可信调用上下文、授权决策、操作/句柄生命周期与结果分派；优先复用现有管理机制，必要的运行中立类型放在 client-core。
- 各能力服务：沿用或提取现有网络、存储、密码学、通知、配置执行逻辑；只能通过共同管理契约对调用者开放。
- `configuration/`：对应配置能力内部的材料、覆盖、合成、应用编排；不再充当整个客户端能力体系的框架。
- `runtime_host/` 与 `engine-client`/kernel adapter：受管理的内核生命周期与唯一内核执行边界。
- 平台 adapter：负责平台网络/文件/凭据/通知等具体机制，不自行接受未经管理的外部业务请求。
- `plugin-sandbox`：安装、加载、VM 限制与 SDK 调用桥；将请求交给客户端统一入口，不自建网络、存储或配置业务后台。开发实验入口不得作为生产旁路保留。

每项迁移都登记旧入口、新入口及切换证据。切换后移除或封闭旧执行旁路；过渡适配器只能委托新服务，不能长期双写或双执行。对应内置功能已经迁入某能力后，即可按授权条件接它的插件桥，不必等待所有无关模块重写；最终所有对外能力都须完成此迁移。

持久数据变更有 schema 版本和中断恢复规则，迁移完成后只有一个写入口，发布时明确旧版本兼容范围。普通用户原文件不擅自删除；不通过迁移把受保护材料降级成普通可读存储。

## 8. 分阶段交付

| 阶段 | 实际工作 | 完成条件 |
| --- | --- | --- |
| P0 入口与责任盘点 | 盘点内置、插件、外部入口到网络/存储/配置/内核的真实路径；明确状态与资源所有者、重复实现、内核契约及旧数据迁移范围 | 入口—能力—执行点矩阵、旁路清单、最小验收场景与兼容边界明确；已有 readiness 失败先归因，不盲目重跑 |
| P1 统一入口与管理契约 | 固定调用身份、授权、任务、资源句柄、预算与完成处理；接一个现有内置调用和受限插件测试调用 | 两种调用进入同一能力执行实现；身份不能伪造，撤权/预算/结果规则实际生效；不只是接口空壳 |
| P2 迁移现有业务调用 | 按能力迁入内置订阅的网络/数据投递、文件导入、设置操作等；对应 SDK 桥复用入口 | 每迁入一项均关闭旧旁路；内置功能不直接访问网络/存储/内核绕过管理；不同能力仍由专属执行模块负责 |
| P3 完成统一配置执行 | 在同一能力管道内完成材料/覆盖、runtime-only 应用、启动恢复及存储策略；移除完整文件必经依赖 | 普通配置和受保护测试材料共用合成、应用、恢复实现；允许的设置可覆盖；失败不产生明文回退 |
| P4 完成用户授权与受保护数据流 | 完善权限界面、通用网络/存储/密码学/通知 SDK、秘密句柄、敏感出口与停用/卸载清理 | 完整插件数据流仍只经过统一入口；安装不授权；拒绝、撤权和晚到结果无法绕过范围；保护能力验证后才开放 |
| P5 业务场景与多端验收 | ZBoard 插件自行实现登录/公告/订阅业务；各端适配相同客户端能力契约 | 业务全链、内置功能与多端共同验收，按实际能力声明支持；无插件专用执行后台 |

P1 起即实现授权判断，插件测试调用使用宿主显式测试授权；在用户授权 UI 与对应安全约束完成前，不开放新增第三方能力。P2/P3 以依赖关系推进，不能用未完成配置改造当成长期保留旁路的理由。SDK 契约早期进入设计，生产开放逐能力验收，不要求先完成整个客户端重写。

**当前客户端自身的 P0–P4 能力边界及通用插件 SDK v1 已完成代码落地：内核/应用/插件包下载、内置规则更新、系统网络探测、规则产物和设置导入导出、桌面打开与剪贴板、TUN/系统代理/模式切换、诊断任务及日志/诊断出口均进入共同管理入口；插件存储、通知、调度、浏览器回调、用户文件选择、短期秘密/密码学和受保护配置应用也受相同授权与回收约束。全局退出统一撤销资源。详见 [迁移记录](./capability-migration.md) 和 [插件 SDK v1](./plugin-sdk.md)。剩余 P5 是外部插件、跨平台安装与真实服务联调验收。** ZBoard 登录、设备凭证与订阅选择仍由插件及服务端实现。

## 9. 验收与边界

统一性是第一类验收：为同一能力分别从内置入口和插件测试入口触发，确认经过相同管理步骤及同一执行模块；通过调用链证据与架构约束检查禁止的直接依赖，不能仅证明返回值相同。逐项核销网络、存储、配置和内核旁路。

管理验收覆盖伪造身份/句柄、授权过期、拒绝、跨组件资源访问、并发预算、取消与晚到响应、停用卸载、客户端重启及资源释放。组合能力不得扩大原调用者权限；已提交副作用不得虚报已取消，旧任务清理不得影响新的合法运行。

配置验收覆盖文件、内置订阅、插件普通材料和受保护材料的启动、应用、mixed 端口/绕过 IP 修改、切换、重启、断开和恢复。来源切换不能携带错误资源覆盖；提交结果不确定、持久化失败和迁移中断都按真实状态恢复。

保护验收用 canary 检查网络/存储/密码学/配置的全链数据流，覆盖 UI、日志、SQLite/WAL、临时/备份、IPC/debug、诊断以及内核查询事件。签名安装、隐藏按钮或一次内存应用均不能代替该验收。不承诺抵抗本机管理员、内存调试或同进程原生引擎漏洞。

按阶段执行定向测试和必要集成验证；代码冻结后由一个责任方统筹全量回归，不重复运行无变化的通过项。分别报告实际代码、验证、平台结果和缺失契约。只修改客户端时不顺带修改 Zero 或中央目录；缺内核能力先单列需求，不降级保护。当前计划及后续本地改动不默认提交、推送或发布。

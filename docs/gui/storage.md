# 本地存储边界

GUI 的本地持久化按数据性质拆分，避免把所有内容塞进单个配置文件，也避免为简单启动配置引入不必要的数据库依赖。

## SQLite 管理的动态业务数据

应用数据目录下的 `znet-sink.db` 集中管理：

- 代理配置记录、顺序和唯一 active 状态；
- 订阅记录、订阅地址、启用状态；
- 订阅到代理配置的 `targetProxyConfigId` 外键映射；
- 按可信调用主体隔离的普通能力存储；当前用于订阅和规则的重试/冷却快照；
- 普通订阅候选与已确认应用后的本地恢复账本，独立于上述每值 64 KiB 的 capability byte store。

代理配置和订阅的关联变更在同一个即时事务中提交。删除代理配置时，引用它的订阅映射会同步清空，避免内存状态和持久化状态分叉。

## 继续使用文件的数据

| 数据 | 存储 | 原因 |
| --- | --- | --- |
| 应用启动与 UI 简单配置 | `app-config.json` | 可读、可恢复，启动阶段无需先打开数据库 |
| 规则集语义数据 | `rule-sets.json` | 保持规则集独立文件边界 |
| 编译后的规则集 | `.zrs` | 由 Zero 直接消费的版本化产物 |
| 用户显式导出的配置 | 独立 JSON | 用户导出产物；托管启动使用最小 bootstrap，再应用内存配置 |
| 日志、调试帧、连接历史 | JSONL/独立文件 | 追加写与轮转模型，不属于配置关系数据 |

## 旧版本迁移

首次打开数据库时，Rust 会在单个事务中导入原有的 `proxy-configs.json` 和 `subscriptions.json`。导入成功后在数据库元数据中记录完成状态，后续启动不再重复导入；旧文件不会自动删除，可作为升级后的人工备份。缺失的代理配置引用会在迁移时清空。

`rule-sets.json` 不参与这次迁移。

2026-09-12：schema 2 在同一数据库新增能力存储表与单调版本计数，从 schema 1 事务升级，保留已有关系数据。旧客户端不支持 schema 2，会拒绝打开；不可把这一变更当作可直接降级。普通存储额度、授权、事务及定时检查点的恢复边界见 [客户端存储、执行与定时边界](./client-state-boundaries.md)。它不提供受保护材料的加密保证。

## 普通订阅恢复账本（schema 3）

schema 3 事务升级保留既有配置、订阅和 capability storage，新增 `ordinary_subscription_recovery` 与单调版本计数。旧客户端拒绝更高 schema；不能把新增表当作可直接降级。表和关系变更沿用 SQLite 的即时事务、CAS、WAL/FULL 和私有文件权限。

账本只接收普通 Zero 来源及候选，拒绝托管/受保护正文。生产准入还要求活动配置的真实运行变更且不需外部 OS 系统代理 retarget；离线/无运行变更保存及需要真实 retarget/补偿的事务继续使用既有链路，不成为本批本地恢复证据。每项候选 JSON（profile 与最终 subscription 合计）最多 16 MiB，元数据最多 64 KiB，账本逻辑材料合计最多 64 MiB、最多 32 项未完成；同一订阅最多一项未完成记录。64 MiB 计入 UTF-8 recovery/source ID、元数据 JSON 与候选 JSON 的字节总量，在实际更新事务内核对；不是 SQLite 文件、页或 WAL 开销的硬上限。容量、磁盘不足、记录损坏或 revision 冲突会明确失败，不删除配置来腾空间，也不以普通 capability storage 存大正文。

阶段为 `prepared → apply-pending → runtime-confirmed → local-committed → complete`。准备事务同时写候选、摘要和来源屏障；只有真实 runtime-only 回执持久确认后才能发布本地候选。`local-committed` 的关系变更与阶段在同一事务保存，来源仍保留屏障；独立 AppConfig 投影确认后，完成事务发布最终来源、移除屏障并清除候选正文。最多保留最新 32 项完成元数据，按版本清理旧完成项，不自动丢弃未完成证据或用户材料。

普通候选本来可能包含代理凭据或来源 URL token，只能留在应用私有关系存储；这不是受保护材料的加密通道。元数据仅保存身份、版本、阶段及来源/材料/各阶段关系图/AppConfig/独立 typed 规则集/有效配置/接管计划摘要与已确认运行身份；不保存 AppConfig 正文、旧明文运行配置、可重新执行的请求或完整内存 Receipt。独立规则集只留摘要，不持久其他托管规则正文；pending 存在性与元数据查询不读取大候选 JSON。UI、通用日志、诊断和设置迁移不导出候选、来源秘密或这些内部记录。

SQLite 与 `app-config.json` 不能跨文件原子提交。重启分别加载两 store，既有设置迁移或备份恢复也可能改变投影；恢复必须核对实际前后阶段及当前来源、关系、设置和运行身份，不能凭内存、当前 revision 或旧 `lastError` 自动宣布成功。重复恢复只接受仍精确匹配的完成记录，不再次发布材料或更新时间。条件 HTTP validator 独立保存，未包含在本地恢复完成收据中，不能补造或重复下载来替代。

接口与未知结果边界见[普通订阅核对与有限恢复](./ordinary-subscription-reconciliation-v0.0.3.md)。测试运行结果由[统一验证记录](../verification/mobile-client-v0.0.3.md)列出；上述持久化不等于移动平台服务或真机恢复验收。

## 应用配置恢复

`app-config.json` 保存时先在同目录写入临时文件并同步，再原子替换主文件；上一次可解析的配置保存在 `app-config.json.bak`。首次保存也建立备份。备份写入失败时保留原主文件，已损坏的主文件不会覆盖有效备份。

启动读取主文件失败时尝试备份。恢复前将原始损坏内容保留为 `app-config-corrupt-*.json`，随后原子恢复主文件并记录日志。主文件和备份均不可用时返回错误，由启动层记录后采用默认值；损坏文件继续保留，后续保存不会静默覆盖它。Unix 下新建的配置、备份和损坏副本均为私有文件。

这套恢复机制用于应用配置文件，不替代 SQLite 事务或规则文件的持久化策略。

## 内核安装备份

每次替换内核前，在应用数据目录的 `kernel-rollback/upgrade-*` 中保留即将改写的二进制、伴随文件、安装清单，以及 `previous-app-config.json`。`receipt.json` 记录目标目录和 `pending`、`committed`、`rolled_back` 状态。准备阶段配置备份失败时，以 `cancelled` 结束事务，不改写仍在运行的旧二进制。文件通过同目录临时副本原子替换，运行中的旧内核在下载和预检查期间继续工作。

安装或恢复运行状态失败时自动尝试回退。回退未完成时错误中返回备份路径和逐项失败原因；成功安装也保留备份。目前没有备份自动清理和强制终止升级后的启动时自动续回退。失去活跃事务的 `pending` 或无法解析的记录会阻止启动、看门狗重启和再次升级，并返回备份位置；记录仍需人工检查后恢复，不能视为已完成安装。

## SQLite 加固

- 使用 `rusqlite` 的 bundled SQLite，避免依赖终端机器上版本不一致或缺失的动态库；
- 固定 application ID 和显式 schema version，拒绝误用其他应用数据库或打开更高版本 schema；
- 启用外键、`WAL`、`synchronous=FULL`、5 秒 busy timeout 和事务性迁移；
- 启用 defensive mode，关闭 trusted schema、writable schema 和双引号字符串兼容行为；
- 启用 secure delete、启动完整性快速检查、JSON 合法性/大小约束和订阅 URL 长度约束；
- 所有值都通过 SQL 参数绑定，不拼接订阅地址或配置内容；错误与日志不输出订阅地址；
- Unix 下数据库及 WAL/SHM 文件权限收紧为 `0600`；Windows 下继承应用数据目录的用户 ACL。

数据库不是用户配置接口。用户可编辑的简单设置仍通过 `app-config.json` 或 GUI 命令维护，数据库 schema 仅由 Rust 迁移管理。
